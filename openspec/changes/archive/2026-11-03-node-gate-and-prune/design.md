# Design

## Context

现状里已经有一套"等待"的现成机制：runner 的调度循环在"没有够格的、也没有在跑的"时，会调 `resumeAwaitingArchive()` 去看 `archive/`，等待名单非空就睡 1 秒再算一轮，不退出。这次要加的"等写好"是同一类东西，可以直接照抄这套形状。

另外三个事实决定了做法：

- 节点的对外状态是固定五种（待跑 / 跑着 / 完成 / 等你 / 失败），存在 `pipeline.json` 里；「等你」本来就有"这一轮停住、等人处理"的意思。
- 面板手上已经有每一格的仓库事实：`nodeRepoState` 为图里每一格都算了 `exists`、`hasTasks`、`taskDone/taskTotal` 和 `planning`（`openspec status` 的 `isPlanningComplete` 与缺哪几件），所以区分两种「等你」不用改 schema。
- `wire` 和 `plan` 的名字校验不是一套：`wire` 把"在 `archive/` 里"当成合法名字，`plan` 一个名字都不查。

约束（来自项目背景）：两个半身的 `apply()` 都不许抛异常；新增注册动作要单独兜底；新增行为要配一个离线回归脚本；规格用中文写，正文必须出现 MUST。

## Goals / Non-Goals

**Goals:**

- 没达到执行标准的格子可以留在图里，但拉不起对话；标准一旦满足就自动放行，不需要人再点一次。
- 已归档、已找不到的格子能一键清掉，清掉之后 Agent 也不能用 `wire` / `plan` 把它们画回来。
- 判定口径只有一处实现，整批开跑、手动启动、清理用的是同一套事实。

**Non-Goals:**

- 不做自动清理。清不清、什么时候清，由人点。
- 不改 `add-all` 的"可加"口径，也不改列表单击加节点的规则：没写完的 change 照样能进图。
- 不给"还没写好的格子"造新的面板视图，沿用现有的待处理列表，只换文案和按钮。
- 不改 `pipeline.json` 的字段，不加新状态。
- 不管"任务全勾了只差归档"的格子怎么收尾——那是「归档」按钮的事。

## Decisions

### 等写好照抄等归档的等待机制

循环里加一组 `awaitingReady`，和 `awaitingArchive` 并排：

- 每一圈算出"前置都满足"的候选时，先过一道执行标准；不够格的记「等你」+ 原因，塞进 `awaitingReady`，不 spawn。
- 空闲分支里先 `resumeAwaitingReady()` 再看 `awaitingArchive`；两组等待任意一组非空就睡一拍再算。
- 有格子在等的时候，即使别的格子还在跑，也要每隔约一秒醒一次，否则一个跑十分钟的对话会把等待拖成十分钟，和"写完自动放行"对不上。

**为什么不在 `runNode` 里拒绝**：那样这一轮就直接收工了，没有人在看仓库，用户只能自己回来点「开始」——和"一旦识别到它已经被写完就开始放行"直接冲突。

**代价**：等待期间 runner 一直活着，面板顶栏一直显示「跑着」。这一条要在文案里说清（在等 N 格写好），并且「停止」随时能收工。

### 不加新状态，用「等你」+ 仓库事实现场区分

「等你」已经有两种成因：没归档、没写好。状态不区分，面板用手上现成的事实区分：

```
status === 'needs_human'
  ├─ 没有任务清单，或 planning.complete === false  → 等写好：不配「归档」按钮，写明差什么
  └─ 其它                                           → 等归档：照旧配「归档」按钮
```

**备选**：给节点加一个 `waiting` 字段。否决理由：要动 `pipeline.json` 的字段表、要兼容老文件，换来的只是面板少算一次判断。

### 执行标准三条，第三条允许降级

1. `openspec/changes/<change>/` 目录还在；
2. 那个目录里有 `tasks.md` 且至少一条任务；
3. `openspec status` 读到这一格的 `isPlanningComplete` 为真。

前两条是文件事实，任何机器上都判得了。第三条只在 CLI **明确返回"不完整"**时拦：命令不可用、执行失败、或者输出里根本没有这一格，都当成"读不到"，不拦。

**为什么不用 `openspec list` 的 `status`**：`no-tasks` 分不清"只写了提案"和"四件套只差 tasks"，而这两者对"能不能开工"不一样——前者让对话凭空开工，后者差一步就能 apply。

**为什么规划判据可以降级而任务清单不行**：没有 `tasks.md` 就真的没活可干，对话只能自己编；而 CLI 读不到是我们这边的问题，不该让整张图停摆。

判据复用 `nodeRepoState`，不新读一遍仓库。

### 整批等，单格拒

同一个判据，两个入口两种处理：

- **整批开跑**：其它格子还能跑，等这一格有意义，所以记「等你」并持续等。
- **右键「启动」**：这是人指着这一格说"就它"，等下去没有别的活，所以直接拒绝并把差什么写在按钮下面。也避免起一条只会空等的流水线。

### 清理做成 Host 动作

客户端自己删节点是现成能力（改画布 → `save` → `mergeRunningGraph`），但纯客户端删有两个问题：没法写离线回归（`client.js` 依赖宿主的 React，离线起不来），Agent 也删不了。所以做成 Host 动作 `prune`：

- 面板按钮打 `/action`，把当前画布一起送过去（照抄 `archive` 的 `state` 兜底：写盘刚好失败时也不能让 Host 用旧图）。
- 工具也加一个 `prune`，和 `plan` / `wire` / `remove` 并列。
- 运行中允许：清理范围只有"已归档 / 已找不到"，正在跑的格子本来就不在里面；入口仍然显式挡一次 `ACTIVE`，防止以后有人放宽范围。

### `wire` 跳过，`plan` 整单拒绝

两种口径对应两种错误：

- **整单拒绝**对付的是"名字写错"——画出一格永远不跑的格子，人还以为这一批包含它。
- **跳过并回报**对付的是"真名字，但已经跑完了"——用户想把能跑的接上，不该因为一个已完成的成员整单失败。

`plan` 声明的是"整张图就是这些"，里面出现不能执行的格子就是声明写错了，所以整单拒绝（顺带补上它现在完全没有的名字校验）。

`after` 指向一个已归档的名字时，当成"这条等待已经满足"吃掉，不报错——否则一批里只有一个已归档的上游，整单就画不出来。

### 清理连带摘线是安全的

整批 runner 认前置 `status === 'done'`，手动启动认「跑完或已归档」。删掉一个已归档的前置，下游只是提前一格变够格——那本来就是它该跑的时候，两种口径结论一致。

## Risks / Trade-offs

- **runner 可能长期活着**：等写好的格子可以等很久。缓解：顶栏和待处理列表写清"在等 N 格写好"，「停止」随时能收工；不打算做"等超过多少时间自动收工"，那会让"写完自动放行"变成看运气。
- **规划判据可能过严**：某个仓库的流程不写 `design.md`，那一批格子会一直被拦。缓解：等待说明里写清差哪一件；这属于"补产物或换 schema"，不是插件替人决定的。要写进 README 的已知限制。
- **等待有开销**：每个等待 tick 都要读仓库状态。靠 `cliChanges` / `cliPlanning` 的 3 秒缓存，把子进程压在最多 3 秒一次；`nodeActivity` 只对等待中的格子算。
- **`wire` 跳过后批量结果的完整性**：回报必须显式列出跳过的名字和原因，否则人以为整批接好了。
- **清理没有撤销**：删了就是删了，和现有「从图里删掉这一格」一样。所以范围只放"永远不可能再执行"的两类，别的都不许进来。
