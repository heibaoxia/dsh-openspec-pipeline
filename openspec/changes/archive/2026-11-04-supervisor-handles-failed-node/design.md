# Design

## Context

监工现在只有两个出手时机，都在 `Runner.runNode` 和 `reportArchives` 里，直接调 `notifySupervisor`（`lib/index.js`）。`notifySupervisor` 自己有五个静默 `return`：没开、没 sessionId、两分钟内重复、读不到会话、宿主没有投递能力。只有投递本身抛错才会写 `lastError`。

`waitForTurnEnd` 每 500 毫秒读一次 `session.snapshotEvents(cursor)`，只认 `turn/end`，没有超时。`node.sessionId` 和 `supervisor.sessionId` 各自唯一，重开一次就覆盖旧的 —— 所以「换新对话、老的不管」在数据层面天然成立。`start-node`（只跑一格、新开对话）已经实现但只给面板用，没进工具枚举。参照 `proposal.md` 的动机。

## Goals / Non-Goals

**Goals:**

- 失败在「发生的那一刻」就变成一张能落地处理的值班单，不依赖任何定时器。
- 监工拿到单子后，能用**一句话**把那一格救回来，而且默认复用原来的对话。
- 监工能"看"而不"说"，用来判断原对话还能不能用。
- 投递失败、监工不在、处理没完成，三种情况都留痕，不静默。

**Non-Goals:**

- 不做全局定时扫描。正在跑的格子本来就在 runner 的 500 毫秒轮询里，加一个定时器只是第二个更慢的观察者，还要解决「哪些仓库开着监工」的枚举问题。
- 不做自动重试。救不救、怎么救，由监工按手册判断。
- 不改「一个仓库同时只跑一条流水线」这条约束。
- 不给节点保留历史会话列表。`sessionId` 仍然只有一个，覆盖即脱钩。

## Decisions

### 1. 失败收敛成一个出口

新增 `failNode(root, state, node, reason, { session, notify })`：记状态、落盘、推一次面板刷新、投值班单，四件事一起做。现有五条失败出口全部改成调它，不再各写各的。

为什么：现在五个出口里只有两个会通知（paused / stuck 那两条根本不在失败路径上），以后再加出口还会漏。收敛成一个函数，漏报在结构上就不可能发生。

备选：在五处各补一次 `notifySupervisor`。否 —— 它解决今天的问题，不解决明天新增出口的问题。

### 2. 卡住的判定放在 `waitForTurnEnd` 里，不另起定时器

`waitForTurnEnd` 本来就在每 500 毫秒读一次事件流。给它加一个 `lastProgressAt`：读到新事件就更新；超过阈值没有新事件就返回 `{ kind: 'stalled' }`。调用方拿到后取消那一轮（`controller.cancel({ sessionId })`）、走 `failNode`、收工。

为什么不用全局定时器：宿主重启后内存里没有任何「哪些仓库开着监工」的名单，定时器要自己解决枚举（读 `workspaceRegistry` 逐个读 `pipeline.json`），还要处理进程生命周期和测试里的假时钟。而 runner 本来就在读这份数据，边际成本几乎为零。

阈值：默认 15 分钟，`DSH_OPENSPEC_STALL_MS` 可覆盖，`0` 关闭。10 分钟下限写进规格，因为一个长工具调用期间确实可能没有任何事件。

### 3. `revive` 复用 runner，加一个 `attach` 模式

`PipelineRunner` 新增 `options.attach`：这一格**不新建会话**，直接用 `node.sessionId`，把监工给的话当下一句话投进去，然后走完全一样的「等收尾 → 看归档 → 记完成 → 往下跑」。`from` 池照旧只覆盖这一格和它的下游。

关键顺序：先记 `from = session.seq`，再投话，再开始等。反过来的话会读到上一轮的尾巴，或者漏掉新的一轮。

拒绝条件都放在动作入口，不放在 runner 里：没有原对话（且没 `fresh`）、仓库已有 runner、这一轮还没结束（且没 `cancel`）。三条都返回一句人话，让监工知道下一步该干什么。

备选：

- 给 `tell` 加一个 `resume` 开关。否 —— 状态变化藏在「说一句话」的动作里，事后翻记录看不出是谁把节点从失败改回跑着的。
- 给 `run` 加 `from`。否 —— `run` 的语义是「重跑」，会给每一格新开对话、把所有失败格子放回待跑，和「接着这一格」是两件事。

### 4. `fresh` 复用 `start-node`，老对话自然脱钩

`fresh: true` 时走 `start-node` 那条路：新建会话、`markNode({ sessionId })` 覆盖旧 id。覆盖之后插件再也不会往老对话发话、也不再等它收尾 —— 「老的不用管了」不需要额外清理。

第一句话沿用现有口径：`执行 <change> Change`，空行，节点自己的附加提示词，空行，监工的指导。节点原来的配置不因为救活而丢。

### 5. `peek` 只读，复用已有读取函数

`lastAssistantText(session, from)` 已经能读出最后一段助手消息；`turn/end` 的 `reason` 能判断这一轮有没有出错。两者拼起来就是 `peek` 的返回，默认上限 2000 字。

不发任何话、不建会话、不改状态。读不到时返回「读不到」，不返回空串 —— 空串会被监工当成「没事」。

### 6. 未处理的失败记在 `supervisor.pending` 里，靠「有机会就补」重投

`pipeline.json` 的 `supervisor` 下面加一个 `pending` 数组，每项记 `{ nodeId, change, reason, at, tries }`。

什么时候补投：`notifySupervisor` 被调用时、以及 `snapshot()` 被面板或 `status` 读到的时候，顺带看一眼有没有到时间的待办；同一个待办两次尝试至少隔 5 分钟。清除条件只有一个：这一格不再是失败状态（被 `revive` 救回来、被 `run` 回收、或者被归档补成完成）。

为什么不做定时器：待办只在出过事之后才存在，天然是稀少事件；挂在一个已经有的、被频繁调用的路径上就够，不需要新的调度设施。代价是「没人开面板、也没有任何新事件」时不会补投 —— 那种情况下用户本来也不在电脑前，等下次打开面板再补投是对的。

### 7. 监工不在也要留痕

`notifySupervisor` 里「读不到会话」「没有投递能力」这两个静默 `return` 改成写 `lastError` + 推一次刷新。成功投递一次照旧清空。

为什么：现在唯一的证据是 `lastAt`，而它只在成功时写。读不到会话时面板仍然显示「值班中 · 上次 20:25」，和真的在值班一模一样。

## Risks / Trade-offs

- **长工具调用被误判成卡住** → 阈值给到 15 分钟、可配、可关；单子里写「可能只是慢，先看一眼再决定」；`revive` 前监工可以用 `peek` 确认。
- **`revive` 之后又失败，导致救活循环** → `pending.tries` 计数，第三次之后单子里明写「已经救过 N 次，建议人来判断」。
- **`fresh` 丢掉上下文，白跑一遍** → 返回值和值班单都明写「老的上下文不再参与，这一格从头做」；节点的说明里也写明是用哪种方式救的。
- **待办重投刷屏** → 5 分钟尝试间隔 + 同一个 `nodeId + reason` 指纹。
- **两个 runner 抢一个仓库** → `revive` 在入口按 `runners` 表拒绝，和 `run` / `start-node` 同一把尺子。
- **网络断的时候监工也跑不动** → 这正是 `pending` 存在的理由：投出去不等于处理了。

## Migration Plan

- `pipeline.json` 只加 `supervisor.pending`；`normalizeSupervisor` 补默认值 `[]`，旧文件直接能读，不需要迁移脚本。
- 新的工具动作是增量：`revive` / `peek` / `start-node` 加进枚举，旧调用不受影响。
- 阈值默认 15 分钟，等于「上线即生效」；出问题可以用环境变量设 0 关掉，不用改代码。
- 版本 0.18.0 → 0.19.0，提交信息 `feat: 监工能救活失败的格子（0.19.0）`。
- 回滚：这三个动作都不改既有数据语义，删掉注册项即可回到当前行为；`pending` 字段留着不影响旧代码。
