# Proposal

## Why

监工只在两种时刻收到值班单：某一格收尾了但没归档、上一格归档了下一格没启动。**两种都以「这一轮正常收尾」为前提**，所以真正出事的那一格，它一个字都收不到。

2026-11-03 的真实一例：`review-redo-permission` 因为网络中断以 `error` 收尾，runner 看见 `reason !== 'completed'`，记成失败就返回了 —— 监工那一行还写着「值班中 · 20:25 投过值班单」。它上一次出手和这一次出事只隔 4 分钟，却完全不知道。

更根本的是，**就算告诉它，它也没有修的办法**：`tell` 把话发进原对话就撒手，节点的「失败」状态不会变、runner 也不会重新盯上它；`run` 虽然能回收失败格子，但会给每一格**新开一个对话从头做**，上下文全丢。监工手上缺的是「把这一格救回来」这个动作。

## What Changes

- **失败必报。** 五种失败出口（模型用不了、会话没挂上、话没送进去、没等到收尾、异常收尾）都必须投一张值班单给监工，单子里带失败原因和这一格最后说的话。
- **卡住也算失败。** 一轮对话长时间没有任何动静（事件流不再推进）时，由 runner 取消那一轮、记失败、投单、收工；不要求人盯着，也不要求监工先自己去取消。
- **监工能动手了：`revive`。** 用一个明确的动作救活一格失败：
  - 默认在**原来的对话**里接着做，把监工给的那段指导当作下一句话；
  - `fresh: true` 时**换一个新对话**重做，那段指导当开头，老对话就此丢下不再管。
  - 这一格回到「跑着」，只接着跑它和它的下游。
- **监工能看了：`peek`。** 只读某一格对话的最后一段内容和有没有出错，不发任何话进去。用来判断「原对话还能用，还是已经被污染了」。
- **单子发不出去、或者监工自己不在，要留痕。** 投递失败和「对话读不到」都写进 `supervisor.lastError` 并让面板用错误色显示，不再静默装作在值班。
- **没人处理的失败不许丢。** 失败的异常记在状态里，投出去的那一轮没能正常收尾（比如网络还没回来）就留着，下一次有机会再投，直到它真的处理过。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `node-run`: 失败不再静默（五种失败出口 + 卡住超时），新增「救活一格」的动作 `revive`（原对话接着做 / `fresh` 换新对话），新增只读动作 `peek`；`start-node` 从只给面板用改成对工具也开放。
- `supervisor`: 值班单多一种出手时机（某一格失败了），值班单和口径里带上 `revive` / `peek` 两个动作；监工不在或投递失败时必须落 `lastError` 并推一次状态；未处理的失败要留着重投。

## Impact

- `lib/index.js`：runner 的五条失败出口与超时判定、`revive` / `peek` / `start-node` 三个动作（工具枚举 + HTTP 入口）、`supervisor` 状态新增字段、`notifySupervisor` 的失败口径、值班单文案。
- `lib/client.js`：面板上「失败」那一格的说明与可操作提示、监工那一行的失败态。
- `test/`：新增离线回归 —— 失败投单、卡住收尾、`revive` 接回原对话、`revive fresh` 换新对话。
- `README`：工具动作表补 `revive` / `peek`，值班监工一节补新的出手时机。
